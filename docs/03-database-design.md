# Health Diary — Database Design Document

**Document ID:** DBD-003  
**Version:** 1.1 (aligned with planned Flyway V1–V15)  
**Status:** V1–V2 applied; V3–V13 prepared, not yet applied or integration-tested  
**Database:** PostgreSQL; Flyway  
**Language:** English identifiers/documentation, Italian user interface  

## 1. Scope and migration status

This document describes the *implemented and prepared migration schema* for the user, service and laboratory/event core. It is not a claim that the full MVP has been migrated. The previous 1.0 design baseline also specified documents and event-document links; those remain **planned, not yet migrated**. V1 and empty V2 are applied and must not be edited. V3–V13 are proposed replacements for the unapplied migrations.

## 2. Identifier policy

All current and newly prepared relational primary/foreign keys use `BIGINT GENERATED BY DEFAULT AS IDENTITY` (or BIGINT foreign keys). V1 already defines `users.id` as BIGINT. This supersedes the previous UUID baseline. Timestamps use `TIMESTAMPTZ`; entered event date/time use DATE/TIME.

## 3. Relationship overview

```text
users ──< medical_services (personal catalog)
users ──< medical_events >── medical_services
users ──< doctors, facilities
medical_services ──< lab_parameters
medical_events ──< exam_results >── lab_parameters
exam_results ──< lab_result_organisms
exam_results ──< lab_microbiology_targets
exam_results >── measurement_units (optional)
medical_events ── 0..1 medical_event_swabs >── swab_sites
medical_services ──< medical_service_options ──< medical_event_options >── medical_events
```

A `LABORATORY` medical event is the laboratory session; there is no `laboratory_exams` table. Multiple `exam_results` can belong to one event, allowing separate bacterial/fungal culture or PCR result rows. A single `exam_result` is the root for repeatable organism or target entries; method is represented by the linked parameter's `group_key` and may be further specified on target/organism rows. The same parameter may occur more than once in one event.

## 4. Tables and constraints

| Table | Migration | Key design |

| `lab_parameters` | V4, seeded V6 | BIGINT PK; service FK; nullable user_id; name, group_key, active flag; allowed groups listed in V4 |
| `doctors` | V7 | BIGINT PK; owner; name, specialization; owner-compatible event FK |
| `facilities` | V7 | BIGINT PK; owner; name, city; owner-compatible event FK |

| `measurement_units` | V8 | BIGINT PK; unique case-insensitive symbol; no automatic unit conversion |
| `exam_results` | V9 | BIGINT PK; event/parameter, position, numeric/text/unavailable value, optional unit, reference interval; unique (exam_id, position) |

### 4.1 Event status

`status` allows `SCHEDULED`, `COMPLETED`, `CANCELLED`; `status_mode` allows `AUTO`, `MANUAL`. In AUTO mode the effective status is computed from local event date/time in the application timezone (initially Europe/Rome), not blindly read from stored `status`. Cancellation is manual. `COMPLETED` is a scheduling state, not proof of clinical performance. Missing report remains a derived state.

### 4.2 Lab results

`value_type` is `NUMERIC`, `TEXT`, or `UNAVAILABLE`. Numeric reference intervals support RANGE/LOWER_BOUND/UPPER_BOUND; textual intervals are stored without numerical interpretation. Unit conversion is not automatic. The backend checks that a result's parameter belongs to its event's LABORATORY service and is accessible to the user; SQL foreign keys alone do not guarantee this.

### 4.3 Microbiology and swabs

The service `Analisi su tampone` is seeded in V5. V6 groups: `SWAB_CULTURE`, `SWAB_MOLECULAR`, `SWAB_ANTIGEN`, `SWAB_MICROSCOPY`. V11 seeds sites (including Vaginale and Altro). V13 links an event to a site; backend verifies it is a swab event and requires text when the site is Altro. Different methods or bacterial/fungal components may be represented by multiple `exam_results` for the same event, each tied to a suitable catalog parameter. `lab_microbiology_targets` stores **negative as well as positive** individual target results; `lab_result_organisms` stores optional organism details (e.g. count, antibiogram).

Example vaginal swab: event for `Analisi su tampone`, site `Vaginale`; culture result text `Nessuna crescita` (bacteriology); separate results for `Candida spp.` positive and Difteroidi, Lattobacilli, Trichomonas vaginalis, Streptococcus agalactiae, Gardnerella vaginalis negative. Preserve original report wording and scope; do not infer that the overall sample was negative.

### 4.4 Deletion and ownership

User-owned clinical records must be scoped to the authenticated owner. Deleting an event cascades to exam results and their organism/target rows and to `medical_event_swabs`. Deleting a referenced catalog parameter/service/unit/site is restricted where indicated in SQL. Global catalog entries are not user-editable. Deleting a user may require explicitly removing dependent records and personal catalog rows in an appropriate order, due to RESTRICT references.

## 5. Not yet implemented in these migrations

`documents`, `event_documents`, medication/therapy, measurement history, vaccinations, allergies, conditions, hospitalizations, operations and export are not created by V1–V15. Document linking and report flags described in the earlier baseline remain future schema work; until then, `report_text` is the only persisted report-content field in this migration set. API validation and integration tests must cover category/ownership invariants, reorder behavior, Flyway migrations, and microbiology examples.

## 6. Important operational notes

- Do not edit V1 or V2; Flyway has applied them.
- Replace the unapplied old V7–V9 with the new ordered V7–V13; **do not leave both copies in the Flyway directory**.
- V3–V6 are included for convenience and are unchanged from the supplied uploads.
- All new schema identifiers are BIGINT; Java entities and DTOs should use `Long` IDs.
- `updated_at` requires consistent application-managed updates or triggers.
- This package is statically checked, not database integration-tested.


## 7. Donations and eligibility assessments (V14)

`donations` is a single user-owned table for both eligibility assessments (`record_type = ELIGIBILITY`) and actual donations (`record_type = DONATION`). Supported `donation_type` codes: `WHOLE_BLOOD`, `PLASMA`, `PLATELETS`, `HEMATOPOIETIC_STEM_CELLS`, `OTHER`. For an eligibility assessment the type may be unknown (`NULL`); for a donation it is mandatory. Stem-cell donation collection route (bone marrow vs peripheral blood) is not separately modeled yet and can be recorded in `notes`.

| Column | Type | Rule |
|---|---|---|
| `id` | BIGINT identity | Primary key |
| `user_id` | BIGINT | Required FK to users |
| `donation_date` | DATE | Required; date of assessment or donation |
| `record_type` | VARCHAR(20) | `ELIGIBILITY` or `DONATION` |
| `donation_type` | VARCHAR(40) | Listed codes; required only for `DONATION` |
| `medical_event_id` | BIGINT | Optional FK to an entire laboratory event, not an individual result |
| `eligibility_result` | VARCHAR(20) | Optional `ELIGIBLE`, `NOT_ELIGIBLE`, `DEFERRED`; only for `ELIGIBILITY` |
| `facility_id` | BIGINT | Optional FK to a user-owned facility |
| `quantity_ml` | NUMERIC(8,2) | Optional positive quantity; only for `DONATION` |
| `notes` | TEXT | Optional notes |
| `created_at`, `updated_at` | TIMESTAMPTZ | Creation and modification timestamps |

Composite foreign keys `(medical_event_id, user_id)` and `(facility_id, user_id)` ensure referenced records belong to the same user. `ON DELETE RESTRICT` prevents accidental removal of an associated event or facility; unlink it first. The backend must additionally verify that the linked event is an `Analisi del sangue` laboratory service and decide whether its date may differ from `donation_date`. One donation record links to at most one medical event, while multiple donation records may reference the same event unless application rules forbid it. A record may have no associated lab event, and a lab event may exist independently.

Example: an eligibility assessment and two whole-blood donations may each link to their own blood-analysis event. Do not infer eligibility from the mere existence of a laboratory report or interpret the clinical results automatically.

**Migration status:** V14 is a proposed new migration, not yet run on PostgreSQL. The previous section's list of unimplemented features remains otherwise applicable.

## 8. Diagnostic service options (V5, V15)

The DIAGNOSTIC category uses generic service families (e.g. `Ecografia`, `Risonanza magnetica (RM)`, `Tomografia computerizzata (TC)`, `Radiografia (RX)`, `Ecodoppler`, `Angio-TC`, `Angio-RM`, `Artro-TC`, `Artro-RM`) and service-specific options seeded in V15. For example, `Ecografia` can have `Tiroide e paratiroidi`, `Transvaginale`, `Articolare`, etc. Options may describe anatomical regions, acquisition routes, or exam subtypes; they are **not** exclusively anatomical sites.

`medical_service_options` references `medical_services` and enforces uniqueness of option names per service. `medical_event_options` links events to zero or more options. It includes `service_id` to ensure each selected option belongs to the event's own service, validated by a trigger; a composite foreign key ensures the option/service pair exists. The trigger also requires category `DIAGNOSTIC`. The frontend shows optional checkboxes only for diagnostic services with options. Other diagnostic procedures (e.g. `Gastroscopia`) remain standalone without options.

The source catalog is editorial and not an official clinical coding system. Options may be freely combined; no clinical compatibility matrix is enforced. More detailed attributes (contrast, side, protocol) can be represented by notes or future structured fields.

Replace the *previous unapplied* V15 anatomical-sites migration with this V15 diagnostic-options migration; do not apply both. V15 requires V7 `medical_events` and V5 seeded services.
